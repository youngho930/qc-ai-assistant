# QC·재고 AI 어시스턴트

**데모** — https://qc-ai-assistant.streamlit.app

사내 재고 데이터와 QC 문서를 함께 조회하는 챗봇입니다.
질문을 받으면 어떤 정보가 필요한지 스스로 판단해 도구를 호출하고,
여러 출처에서 얻은 결과를 합쳐 하나의 답을 만듭니다.

[사내 재고 현황 대시보드](https://github.com/youngho930/inventory-dashboard)에서
이어지는 프로젝트로, 같은 데이터 구조를 그대로 사용합니다.

> 무료 API 한도로 운영되어 일시적으로 응답이 제한될 수 있습니다.
> 며칠간 접속이 없으면 앱이 절전 상태가 되며, 첫 접속 시 깨어나는 데 30초 정도 걸립니다.

## 왜 만들었나

대시보드를 만들어 재고 확인 시간을 건당 1-2분에서 30초로 줄였지만,
줄어든 것은 찾는 시간이었고 판단하는 시간은 그대로 남아 있었습니다.

"S26 밴드 200대 생산하려는데 부속품이 충분한가"를 확인하려면
BOM 화면에서 소요량을 뽑고, 재고 화면에서 부속품을 하나씩 검색하고,
부족한 것이 나오면 협력업체 리드타임을 다시 찾아봐야 했습니다.
데이터는 다 있는데 그것들을 엮는 일이 사람 몫이었습니다.

여기에 검사 기준 확인처럼 문서를 뒤져야 하는 일까지 섞이면
찾아야 할 곳이 더 늘어납니다.

그래서 질문 하나로 이 과정을 끝내는 챗봇을 만들었습니다.

## 동작 방식

```
사용자 질문
    │
    ▼
  Gemini  ──── 어떤 도구가 필요한지 판단 (function calling)
    │
    ├─→ get_inventory                  재고 조회 + 안전재고 대조
    ├─→ get_bom                        BOM 전개 + 소요량 계산
    ├─→ check_production_feasibility   소요량 vs 재고 판정 + 리드타임
    ├─→ get_supplier                   협력업체 연락처·리드타임
    ├─→ lookup_term                    현장 용어 조회
    └─→ search_qc_docs                 QC 문서 검색 (임베딩 기반 RAG)
    │
    ▼
 결과를 종합해 답변 생성
```

한 질문에 여러 도구가 필요하면 순차적으로 호출합니다.
"건식전극 재고 얼마 남았고 부족하면 어디에 발주해야 해?" 같은 질문은
재고 조회와 협력업체 조회를 모두 거쳐 하나의 답으로 돌아옵니다.

어떤 도구가 어떤 인자로 호출됐고 무엇을 반환했는지는
답변 위 접힌 영역에서 전부 확인할 수 있습니다.

## 두 가지 사용자층

같은 데이터라도 묻는 사람에 따라 필요한 설명이 다릅니다.
실무자에게는 결론이, 처음 배우는 사람에게는 맥락이 먼저 필요합니다.

**실무자 모드 (기본)** — 수치를 표로 정리해 바로 판단할 수 있게 답합니다.

**신입 모드** — 시스템 프롬프트를 바꿔 설명 방식을 전환합니다.
용어가 나오면 뜻을 덧붙이고, 수치만 주는 대신 그 기준을 어기면
무슨 일이 생기는지 함께 설명하며, 혼자 판단하지 말고 확인받아야 할
지점을 알려줍니다. 기준 자체는 문서 그대로 전달하며,
쉽게 쓰려고 기준을 바꾸지는 않습니다.

신입이 어려운 것은 답을 못 찾는 것이 아니라 무엇을 물어야 할지
모르는 것이라고 보고, 답변마다 이어서 물어볼 질문 2개를
버튼으로 제안합니다.

## 예시 질문

실무자 모드

- S26 밴드 200대 생산하려는데 부속품 재고 충분해?
- 안전재고 미달인 품목 알려줘
- S26 밴드 출고 전 검사 항목이 뭐야?
- 건식전극 재고 얼마 남았고, 부족하면 어디에 발주해야 해?

신입 모드

- BOM이 뭐예요?
- 부속품이 입고되면 뭘 해야 하나요?
- 불량이 나오면 어떤 순서로 처리하나요?

## 기술

- Python 3.12
- Streamlit — 채팅 UI
- Google Gemini API — 응답 생성 및 function calling, 문서 임베딩
- NumPy — 코사인 유사도 검색

## 설계에서 고민한 것

**벡터 DB를 쓰지 않은 이유** — 문서가 수십~수백 문단 규모라 임베딩을 미리 계산해두고
NumPy 내적 한 번으로 검색하면 충분합니다. Chroma나 FAISS를 붙이면 의존성이 무거워져
무료 호스팅 환경에서 메모리 한도에 걸릴 위험이 커집니다. 필요한 정확도를 얻는 데
가장 가벼운 방법을 골랐습니다. 문서가 수천 건 규모가 되면 벡터 DB로 옮겨야 하는
구조라는 점은 알고 있습니다.

**용어 사전은 RAG가 아니라 별도 도구로** — 정의는 정확히 일치해야 합니다.
유사도 검색으로 뽑으면 비슷하지만 다른 문단이 걸릴 수 있어, 키 매칭으로
조회하는 도구를 따로 만들었습니다. 등록되지 않은 용어를 물으면
지어내지 않고 등록된 목록을 안내합니다.

**후속 질문은 추가 API 호출 없이** — 질문을 따로 생성하려고 모델을 한 번 더
부르면 무료 티어 하루 한도가 절반으로 줄어듭니다. 답변 맨 끝에 정해진 형식으로
붙여 출력하게 하고 파싱해서 분리했습니다. 형식을 지키지 않으면 버튼만
표시되지 않고 답변은 정상 동작합니다.

**색인을 저장소에 커밋** — 임베딩 계산은 문서가 바뀔 때만 필요합니다.
결과를 `index/docs_index.npz` 로 커밋해두면 배포할 때마다 API를 다시 호출하지 않아
무료 티어 요청 한도를 아끼고 앱 시작도 빨라집니다.

**자동 함수 호출 대신 직접 루프** — SDK에 도구를 자동 호출해주는 기능이 있지만,
어떤 도구가 왜 불렸는지 화면에 보여주려고 루프를 직접 구현했습니다.
답이 어디서 나왔는지 확인할 수 없으면 실무에서 신뢰하기 어렵습니다.

**모르면 모른다고 답하게** — 검색 결과의 유사도가 기준 미만이면 문단을 반환하지 않고,
시스템 프롬프트에서 추측을 금지했습니다. 검사 기준을 지어내는 것은
틀린 답을 주는 것보다 위험합니다.

**조회 전용** — 등록·수정·삭제 도구는 만들지 않았습니다. 챗봇이 재고를 직접
바꾸면 ERP 데이터와 어긋나고, 누가 언제 바꿨는지 추적할 수 없게 됩니다.

## 품목명 마스킹에 대하여

로그인하지 않으면 품목명과 품번이 가려집니다 (`S26 밴드` → `S** 밴드`).
모델 식별자만 가리고 `밴드`, `건식전극` 같은 범주명은 남깁니다.
범주까지 지우면 답변을 읽을 수 없기 때문입니다.

**이것은 접근 제어가 아니라 표시 제어입니다.**
데이터 파일이 공개 저장소에 그대로 있으므로 저장소를 열면 원본을 볼 수 있습니다.
실제로 보호가 필요한 데이터라면 서버에서 권한을 확인해 걸러야 하고,
애초에 공개 저장소에 두어서는 안 됩니다.
데모 환경에서 식별자 노출을 줄이려는 목적으로 만들었습니다.

가리는 위치는 UI가 아니라 도구 반환값으로 잡았습니다.
화면에서만 가리면 모델은 원본을 그대로 보게 되어, 표에는 마스킹된 값이 나와도
설명 문장에 원래 이름을 쓸 수 있습니다. 데이터 단계에서 가리면
모델도 가려진 값만 보므로 새어나갈 경로가 줄어듭니다.

비밀번호는 SHA-256 해시로만 보관하며 평문은 저장하지 않습니다.
`python make_password.py` 로 해시를 생성해 환경변수에 넣습니다.

## 알려진 한계

**마스킹이 완전하지 않습니다.** 사용자가 질문에 원본 이름을 직접 쓰면,
모델이 답변 서두에서 그 이름을 그대로 인용하는 경우가 있습니다.
도구가 돌려준 값은 정확히 가려지지만 사용자 입력까지는 통제할 수 없습니다.
출력 텍스트에도 마스킹을 적용하면 이 누수를 막을 수 있으나,
검사 기준의 수치(50kΩ, 3mm)까지 함께 가려져 답변이 무의미해집니다.
데이터 단계 마스킹은 유지하고 출력 단계는 적용하지 않기로 했습니다.
프롬프트로 거는 제약은 보장이 아니라 경향이며, 표시 제어로는 이 정도가 한계입니다.

**마스킹하면 식별자가 겹칩니다.** `FP-105`와 `FP-106`이 모두 `FP-1**`이 되어
구분되지 않고, 그 값으로 다시 조회하면 찾지 못합니다.
로그인 전은 둘러보기용입니다.

**반제품 재고를 반영하지 않습니다.** 반제품이 있어도 하위 부속품 소요량을
그대로 계산합니다. 실제로는 반제품을 쓰면 하위 부속품이 필요 없으므로,
재고를 반영해 전개를 중단하는 로직이 필요합니다.

**대화 문맥이 제한적입니다.** 이전 도구 호출 결과가 아닌 텍스트 답변만
문맥에 남아, 앞 질문을 이어받는 후속 질문이 항상 정확하지는 않습니다.

**협력업체가 `suppliers.json`에 없는 부속품은 리드타임이 비어 있습니다.**

**무료 API 한도가 낮습니다.** 모델에 따라 하루 요청 수가 제한되어,
데모 중 한도 초과 안내가 표시될 수 있습니다.

## 실행 방법

```bash
git clone https://github.com/youngho930/qc-ai-assistant.git
cd qc-ai-assistant

python -m venv venv
venv\Scripts\activate        # Windows
source venv/bin/activate     # macOS / Linux

pip install -r requirements.txt

copy .env.example .env       # Windows
cp .env.example .env         # macOS / Linux
```

`.env` 를 열어 `GEMINI_API_KEY` 를 채웁니다.
API 키는 [Google AI Studio](https://aistudio.google.com/apikey)에서
카드 등록 없이 발급받을 수 있습니다.

관리자 로그인을 사용하려면 비밀번호 해시를 생성해 `.env` 에 추가합니다.

```bash
python make_password.py
```

문서 색인을 만들고 실행합니다. 색인은 `data/docs/` 를 수정할 때마다 다시 생성합니다.

```bash
python build_index.py
streamlit run app.py
```

## 배포

Streamlit Community Cloud 에 GitHub 저장소를 연결하면 배포됩니다.
Advanced settings 에서 Python 버전을 3.12 로 지정하고,
Secrets 에 아래 값을 넣습니다.

```toml
GEMINI_API_KEY = "발급받은_키"
GEMINI_MODEL = "사용할_모델명"
EMBED_MODEL = "사용할_임베딩_모델명"
ADMIN_PASSWORD_HASH = "생성한_해시"
```

모델명을 Secrets 로 관리하면 모델 세대가 바뀌어도
코드 수정 없이 대시보드에서 교체할 수 있습니다.

## 만들며 막혔던 것

**SDK 버전 때문에 도구 호출이 실패했습니다.** 400 오류의 원인을 추적한 결과,
`requirements.txt` 에 고정한 라이브러리 버전이 최신 모델이 요구하는
`thought_signature` 필드를 인식하지 못하고 버리고 있었습니다.
코드가 아니라 의존성이 원인이었습니다. 버전을 고정하면 재현성은 얻지만
API 규격 변경에 막힌다는 점을 실제로 겪었습니다.

**배포 환경의 파이썬 버전이 달라 설치가 실패했습니다.**
기본값으로 잡힌 버전이 너무 최신이라 일부 패키지가 대응되지 않았습니다.
로컬에서 검증한 3.12 로 명시해 해결했습니다.

**`st.secrets` 접근이 예외를 던졌습니다.** `secrets.toml` 이 없는 로컬 환경에서는
`in` 연산자조차 예외를 발생시켜, 예외 처리로 감싸고 `.env` 를 우선하도록 바꿨습니다.
또한 `st.secrets` 접근이 Streamlit 명령으로 집계되어
`set_page_config()` 가 첫 명령이어야 한다는 제약과 충돌했습니다.

## 데이터에 대한 안내

이 저장소의 데이터는 전부 포트폴리오용 가상 값입니다.

- 재고, BOM, 협력업체 데이터는 재고 대시보드 프로젝트의 데모 데이터를 사용했습니다.
  구조는 실제 운영하던 것과 같고 값은 모두 가상입니다.
- `data/docs/` 의 QC 문서와 `data/glossary.json` 의 용어 설명은
  실무 경험을 바탕으로 시연을 위해 직접 작성했습니다.
  실제 사내 검사기준서나 작업지침은 포함되어 있지 않습니다.
